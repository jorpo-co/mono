# mono Skill — Agent Guide

## What mono Is

mono is a git-based monorepo manager. Each project unit (auth, api, web) lives
on its own **orphan branch** inside a single repo. The parent branch pins exact
versions via **git submodules**. Object stores are shared via **bidirectional
alternates** so tagged commits resolve correctly.

Orphan branch means the branch has zero shared commit history with any other
branch — `git log modules/auth/main` shows only auth's commits.

## Agent Workflow

The core pattern for AI agents:

1. **Agent works inside its module** — `cd modules/<name>` — fully isolated
2. **Agent commits changes** inside the module directory
3. **Agent tags a version** via `mono module tag <name> vX.Y.Z`
4. **Human reviews** and pins the version in the parent via `mono module pin`
5. **Deploy** via `mono push`

Multiple agents never touch the same files because each module is a separate
directory with its own orphan branch.

## Architecture

```
repo/
├── main                          ← parent branch, holds gitlink pointers
├── modules/auth/main             ← orphan branch, auth history
├── modules/api/main              ← orphan branch, api history
├── libs/strutils/main            ← orphan branch, lib history
│
├── modules/auth/                 ← submodule working tree (gitlink in main)
├── modules/api/
├── libs/strutils/
│
├── .gitmono                      ← config: roots, default-root, base branch
├── .gitmodules                   ← git submodule declarations
│
└── .git/objects/info/alternates  ← bidirectional object sharing
```

### Key Concepts

| Concept | Details |
|---|---|
| **Orphan branch** | `<root>/<name>/<base>` — e.g. `modules/auth/main`. Zero shared history. |
| **Submodule** | Registered via `git submodule add ./ <path>`. URL is `./` (self-referencing). |
| **Gitlink** | Parent commit stores exact SHA of submodule HEAD. Run `git ls-tree HEAD modules/auth` to see it. |
| **Alternates** | Parent and submodule share object stores bidirectionally. Auto-configured by `module add`, regenerated by `mono setup`. |
| **Root** | Top-level grouping directory. Configured in `.gitmono` as `mono.roots`. Default: `modules`. |
| **Tag prefix** | `<root>/<name>/v<semver>` — e.g. `modules/auth/v1.2.0`. Tags live in parent namespace. |

## Commands

### `mono init`

Initialize a fresh repo as a mono monorepo.

```
mono init [--roots <csv> | -r <csv>] [--default-root <root>]
```

Creates empty root commit, tags `v0.0.0`, writes `.gitmono` config.

**Error:** repo already has commits — bails out.

### `mono module add`

Create new module: orphan branch + submodule + alternates.

```
mono module add [-r <root>] <name>
mono module add <root>/<name>
mono module add [--branch <branch>] <name>
```

Creates orphan branch `<root>/<name>/main` from `v0.0.0`, tags `<root>/<name>/v0.0.0`,
registers submodule at `<root>/<name>/`, sets up alternates, commits addition to parent.

With `--branch`: registers existing branch instead of creating orphan. Used internally
by `mono module split`.

**Errors:**
- Module already exists (branch conflict)
- Root not configured in `.gitmono`
- Ambiguous: `-r` and path both given

### `mono module tag`

Tag module HEAD. Does NOT update parent gitlink (unless `--pin`).

```
mono module tag [-r <root>] [--pin|-p] <name> <semver>
mono module tag [--pin|-p] <root>/<name> <semver>
```

1. Reads submodule HEAD SHA
2. Updates parent branch ref to match
3. Creates parent-level annotated tag: `<root>/<name>/v<semver>`

With `--pin`: also updates parent gitlink + commits in one step.

### `mono module pin`

Update parent gitlink to a tagged version or current HEAD.

```
mono module pin [-r <root>] <name> [<version>]
mono module pin <root>/<name> [<version>]
```

With version: pins to that tag's commit.
Without version: pins to submodule's current HEAD.

Commits the updated gitlink in parent.

### `mono module version`

Show pinned version of a module in current parent HEAD.

```
mono module version [-r <root>] <name>
mono module version <root>/<name>
```

Output: `<tag> (<sha>)` or `<sha> (no tag)`.

### `mono module split`

Convert existing folder into a submodule, preserving history.

```
mono module split <root>/<name>
```

1. `git subtree split --prefix=<path>` extracts folder history to orphan branch
2. `git rm -rf <path>` removes folder from parent tree
3. Commits removal
4. Registers as mono module (equivalent to `module add --branch`)

Requires `git subtree` (Git 2.30+).

### `mono clone`

Full checkout after `git clone`.

```
mono clone
```

Runs `git submodule update --init --recursive` then `mono setup`.

### `mono setup`

Prepare submodules: regenerate alternates + switch to tracked branch.

```
mono setup
```

Idempotent. Safe to re-run after `git pull`.

### `mono push`

Push everything — base branch, all orphan branches, all tags.

```
mono push
```

One command, no forgotten branches.

### `mono config`

Read or write `.gitmono` config.

```
mono config <key> [<value>]
mono config --root-list
mono config --default-root
```

## Module Specification (Three Forms)

All module commands accept these forms:

```bash
# 1. Bare name -> default root
mono module tag auth v1.2.0

# 2. Explicit root via -r
mono module tag -r libs strutils v0.5.1

# 3. Full path
mono module tag libs/strutils v0.5.1

# Error: -r AND path both given
mono module tag -r libs libs/strutils v1.0.0
```

## Tag Naming Convention

| Kind | Pattern | Example | Creator |
|---|---|---|---|
| Root tag | `v0.0.0` | `v0.0.0` | `mono init` |
| Module root tag | `<root>/<name>/v0.0.0` | `modules/auth/v0.0.0` | `module add` |
| Version tag | `<root>/<name>/v<semver>` | `modules/auth/v1.2.0` | `module tag` |
| Orphan branch | `<root>/<name>/<base>` | `modules/auth/main` | `module add` |

## Agent-Specific Patterns

### Work in isolation

```bash
# Agent A — auth module
cd modules/auth
# ... develop ...
git add -A && git commit -m "feat: add 2FA"
cd ../..
mono module tag auth v2.0.0
```

### Upgrade a shared dependency

```bash
cd libs/strutils
# ... change API ...
git commit -m "perf: optimize string ops"
cd ../..
mono module tag --pin libs/strutils v0.6.0
```

Other modules adopt the new version deliberately via `mono module pin`.

### Multi-agent orchestration

- Agent A works `modules/auth/`.
- Agent B works `modules/api/`.
- Agent C works `modules/web/`.
- No file overlap. No merge conflicts.
- Human gates versions: approves tags, pins in parent.

### Bootstrap from clone

```bash
git clone <url>
cd repo && mono clone
# Ready. All modules at pinned versions.
```

## Common Edge Cases

| Situation | Resolution |
|---|---|
| `mono init` on repo with commits | Bails out — start fresh |
| Module already exists | `module add` errors with "module already exists" |
| No origin configured | `mono push` warns per branch/tag but continues |
| Tag already exists | `mono module tag` errors on duplicate tag |
| Module path not found | `module version` errors "module not found in current HEAD" |
| Ambiguous module spec | Pass `-r <root>` OR `<root>/<name>`, not both |
| After `git pull` with new submodule pointers | Run `mono setup` to regenerate alternates |

## Design Principles

Do NOT:

- Use worktrees instead of submodules (worktrees don't pin versions via gitlinks)
- Edit files outside your module's directory
- Pin a version in parent without verifying compatibility
- Forget to push orphan branches (`mono push` handles this)
- Assume module branches exist after clone without `mono clone` or `mono setup`
